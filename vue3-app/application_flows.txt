APPLICATION FLOWS - NEU Study Central Server Management System (admin console)
Traced from the Vue 2 source (components, Vuex store, router, permission guard,
axios interceptors, api modules) and confirmed against the Vue 2 baseline
screenshots in before_migration/.

================================================================================
A. AUTHENTICATION
================================================================================
A1. Successful login
 1. The user opens the application at "/" without an Admin-Token cookie.
 2. The router guard sees no token, so it redirects to "/login?redirect=/".
 3. The login screen renders with username and password pre-filled with "admin".
 4. The user presses "Sign in" (or Enter in the password field).
 5. The form validates: the username must be "admin" or "editor", the password
    at least 5 characters.
 6. The login action stores the token "admin" in the store and writes the
    Admin-Token cookie.
 7. The button leaves its loading state and the user is pushed to the redirect
    target ("/"), which redirects on to "/dashboard".
 8. The guard now finds a token but an empty roles list, loads the profile
    (name "admin", roles "admin", avatar URL) and lets the navigation finish.
 9. The layout renders: dark sidebar, navbar with avatar, dashboard text
    "name:admin" and "roles:admin".

A2. Failed login - invalid username
 1. The user clears the username and types a value other than admin/editor.
 2. On blur, and again on submit, the validator fails.
 3. The field turns red and shows "Please enter correct username"; no request is
    sent and the route does not change.

A3. Failed login - short password
 1. The user types a password shorter than 5 characters and submits.
 2. The validator fails with "Password cannot be less than 5 characters"; no
    request is sent.

A4. Guard redirect of a protected route
 1. An unauthenticated user requests "/#/campusset/list".
 2. The guard redirects to "/login?redirect=/campusset/list" and stops the
    progress bar.
 3. After a successful login the user lands directly on /campusset/list.

A5. Already-authenticated user opens the login page
 1. A user holding an Admin-Token cookie requests "/#/login".
 2. The guard redirects to "/" and stops the progress bar.

A6. Logout
 1. The user clicks the avatar in the navbar; the dropdown opens with "Home" and
    "LogOut".
 2. The user clicks "LogOut".
 3. The token and roles are cleared, the Admin-Token cookie is removed and the
    page is reloaded.
 4. The reloaded application has no token, so the guard sends the user to the
    login screen.

A7. Forced logout on an expired/illegal token
 1. Any API call returns a body with code 50008, 50012 or 50014.
 2. The response interceptor shows the body message as an error toast and opens
    the confirmation dialog titled "log out".
 3. If the user confirms, the session is cleared and the page is reloaded,
    landing on the login screen. If the user cancels, they stay on the page.

================================================================================
B. NAVIGATION
================================================================================
B1. Sidebar navigation
 1. The sidebar is built from the router configuration, skipping hidden routes.
 2. "Data Management" is an alwaysShow parent, so it renders as a sub-menu with
    the child "Data Dict".
 3. "Campus set" renders as a sub-menu with the visible children "Campus Set
    List", "Campus Set Add" and "Campus List".
 4. Clicking an entry navigates to its resolved path, the entry becomes active
    (text #409EFF) and the content area fades in the new page.

B2. Breadcrumb
 1. On every route change the breadcrumb is rebuilt from the matched named
    routes, always prefixed with "Dashboard".
 2. Intermediate crumbs are links; the current (last) crumb is grey plain text.
 3. Clicking an intermediate crumb navigates to its redirect target, or to the
    crumb path with the current route parameters substituted.

B3. Collapsing the sidebar
 1. The user clicks the hamburger icon in the navbar.
 2. The icon rotates, the sidebar shrinks to 36 px, the main container shifts
    left and the "sidebarStatus" cookie is set to 1.
 3. Clicking again restores the 180 px sidebar and sets the cookie to 0.

B4. Mobile/responsive behaviour
 1. The layout measures the body width on mount and on every window resize.
 2. Below 1024 px the device mode becomes "mobile" and the sidebar is closed
    without animation.
 3. In mobile mode the sidebar overlays the content with a dark drawer
    background; clicking the background, or changing the route, closes it.

B5. Unknown route
 1. The user requests a path that matches no route.
 2. The catch-all route redirects to "/404" and the 404 screen is shown with
    "OOPS!", the animated clouds and a "Back to Home" link.

================================================================================
C. CRUD - CAMPUS SET
================================================================================
C1. Browse the campus-set list
 1. The user opens /campusset/list.
 2. The screen requests page 1 with 5 records per page, posting the (initially
    empty) search object.
 3. The table shows selection checkboxes, campus name, campus code, API url,
    contact name, contact phone, the online/offline status and the operation
    buttons; the pagination shows the total.

C2. Search the campus-set list
 1. The user types a campus name and/or a campus code.
 2. The user presses "Search"; the list reloads from page 1 with those filters.

C3. Create a campus set
 1. The user opens /campusset/add (sidebar entry "Campus Set Add").
 2. The user fills campus name, campus code, API url, contact name and phone.
 3. The user presses "Save"; because the record has no id, a create request is
    sent.
 4. On success a "Saved!" success toast is shown and the user is navigated to
    /campusset/list.

C4. Edit a campus set
 1. The user presses the pencil button of a row, navigating to
    /campusset/edit/<id>.
 2. The screen loads that campus set and fills the form with it.
 3. The user changes a value and presses "Save"; because the record has an id an
    update request is sent.
 4. On success an "Updated!" toast is shown and the user returns to
    /campusset/list.

C5. Delete one campus set
 1. The user presses "Delete" in a row.
 2. The confirmation dialog "It will delete this record." (title "Notice",
    buttons "Yes"/"Cancel") opens.
 3. On "Yes" the record is deleted, a "Deleted!" toast is shown and the list
    reloads from page 1. On "Cancel" nothing happens.

C6. Delete the selected campus sets
 1. The user ticks one or more rows.
 2. The user presses "Delete All Chosen Records".
 3. The confirmation dialog "It will delete all these chosen record." opens.
 4. On "Yes" the collected ids are sent as one batch-remove request, a
    "Deleted!" toast is shown and the list reloads from page 1.

C7. Lock / unlock a campus set
 1. For an online row the user presses "Lock"; status 0 is sent and the list
    reloads.
 2. For an offline row the user presses "Unlock"; status 1 is sent and the list
    reloads.

================================================================================
D. CRUD - CAMPUS
================================================================================
D1. Browse and filter the campus list
 1. The user opens /campusset/campus/list.
 2. The screen loads page 1 with 10 records per page and the list of states
    (dictionary code "State"); the table shows a loading mask until the data
    arrives.
 3. The user picks a state; the city list and the selected city are cleared and
    the cities of that state are loaded.
 4. The user optionally picks a city and/or types a campus name.
 5. The user presses "Search"; the list reloads from page 1 with those filters.
 6. Changing the page size reloads the list from page 1 with the new size.

D2. Take a campus online / offline
 1. For an online row the user presses "Offline"; status 0 is sent and the list
    reloads from page 1 (the button flips to "Online").
 2. For an offline row the user presses "Online"; status 1 is sent.

D3. View campus details
 1. The user presses "Details" in a campus row, navigating to
    /campusset/campus/show/<id>.
 2. The screen loads the campus and its booking rule and renders the "Basics"
    table (name, type, logo, code, address, route, introduction) and the
    "Reservation Rules" table (cycle, start/end time, cancel time, rule list).
 3. The user presses "Back" and returns to the campus list.

D4. View a campus schedule
 1. The user presses "Schedule" in a campus row, navigating to
    /campusset/campus/schedule/<campuscode>.
 2. The department tree of that campus is loaded and fully expanded, and the
    first leaf department is selected automatically.
 3. The schedule rule page for that department is loaded: date tags with
    available/reserved counts, the total for the pagination and the schedule
    rows of the first date.
 4. The user clicks another date tag; that tag becomes active and the schedule
    rows for that date are reloaded.
 5. The user clicks another department leaf; the date pagination resets to page
    1 and the whole panel reloads. Clicking a department category does nothing.
 6. The user pages through the dates with the prev/next pagination; the selected
    date resets to the first date of the new page.

================================================================================
E. DATA DICTIONARY
================================================================================
E1. Browse the dictionary tree
 1. The user opens /cmn/list.
 2. The root entries (children of id 1) are loaded and shown with name, code,
    value and create time.
 3. Expanding a row lazily loads and resolves the children of that entry.

E2. Import dictionary data
 1. The user presses "Import"; the dialog titled "Import" opens with a file
    upload and the tip "Excel files only and maximum size is 500kb".
 2. The user uploads a file; on success an info toast "uploded successfully!" is
    shown, the dialog closes and the root list reloads.
 3. Pressing "Cancel" closes the dialog without uploading.

E3. Export dictionary data
 1. The user presses "Export".
 2. The browser navigates to the export endpoint and downloads the file.

================================================================================
F. FORM SUBMISSION (demo form screen)
================================================================================
F1. The demo form collects activity name, zone, date, time, delivery switch,
    activity types, resource radio and a description.
F2. Pressing "Create" shows the message "submit!".
F3. Pressing "Cancel" shows the warning message "cancel!".

================================================================================
G. SEARCH & FILTER (demo tree screen)
================================================================================
G1. Typing in the filter field filters the tree to the nodes whose label
    contains the typed text; clearing the field shows all nodes again.

================================================================================
H. ERROR HANDLING
================================================================================
H1. Business error (code != 200)
 1. A request returns a body whose code is not 200.
 2. An error toast with the body message is shown for 5 seconds and the calling
    promise is rejected, so the screen keeps its previous data.

H2. Transport error / backend down
 1. A request fails or times out after 5 seconds.
 2. An error toast with the transport error message is shown for 5 seconds; the
    tables stay empty (or keep their loading mask, as in the baseline campus
    list screenshot taken without a backend).

H3. Session error (50008 / 50012 / 50014)
 1. See flow A7: the toast is followed by the "log out" confirmation dialog.
